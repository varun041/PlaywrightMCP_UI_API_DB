# Playwright + TypeScript BDD Automation Framework (UI / API / DB)

An end-to-end test automation framework built with **Playwright**, **TypeScript**, and **Cucumber-style BDD** (via `playwright-bdd`), designed to exercise all three layers of an application from a single repo:

- **UI** — Page-Object-Model browser automation against the React frontend
- **API** — HTTP-level testing of the Express REST backend
- **DB** — direct SQLite assertions against the underlying data, run against an isolated per-run copy of the database

The application under test is the **Banking Customer Management App** (`banking-app/`), a full-stack Node.js/Express + React + SQLite app. This framework was built and is maintained iteratively with **Claude Code**, using **MCP (Model Context Protocol) servers** and a set of purpose-built **subagents** (see [AI Agents Used](#-ai-agents-used)) to plan, generate, run, and heal tests directly from the coding assistant.

## 🤖 AI Agents Used

This framework is built and maintained iteratively with Claude Code. Three specialized subagents (defined under `.claude/agents/`) each own a distinct part of the test lifecycle, driving a real browser through the **playwright-test** MCP server rather than writing tests blind:

| Agent | Role |
|---|---|
| **playwright-test-planner** | Explores the running application live (navigating, clicking, inspecting the DOM) and produces comprehensive markdown test plans — happy paths, edge cases, negative/validation scenarios — saved under `specs/`. |
| **playwright-test-generator** | Takes one scenario from a test plan and generates a real Playwright spec by executing each step live against the browser, then writes out the resulting test file with per-step comments matching the plan. |
| **playwright-test-healer** | Runs the suite, and for every failure, debugs it step-by-step against the live browser (inspecting selectors, console/network activity, timing) before editing the code and re-running until green. Falls back to `test.fixme()` with an explanatory comment only when a failure is a confirmed application gap rather than a test defect. |

In practice, the healer agent has already root-caused and fixed real product issues in this repo rather than just papering over failing tests — for example:
- A SQLite connection-per-query bottleneck in `banking-app/backend/db.js` that caused severe latency under parallel test workers — fixed by switching to a single persistent connection with WAL mode.
- A React state race in `CustomerList.jsx` / `CustomerDetails.jsx` where an older, slower API response could resolve after a newer one and silently overwrite fresh UI state — fixed with a request-sequencing guard.

## 🔌 MCP Integration

This framework is driven from Claude Code using MCP servers configured in `.mcp.json`:

| Server | Purpose |
|---|---|
| **playwright-test** | Drives a real, live browser (navigate, click, fill forms, snapshot the DOM, inspect network/console) so the planner/generator/healer agents above can plan, author, and debug tests interactively instead of writing them blind. Also exposes `test_run`/`test_debug`/`test_list` for running and debugging the actual Playwright suite. |
| **github** | Reads/writes the repo (files, branches, PRs, issues) directly from the coding assistant without needing a separate `git` shell for those operations. |

Direct **database** access (seeding, verifying schema, cross-checking API responses against the source of truth) is done in-process via `src/services/DbService.ts` and the `db` fixture, using the `sqlite3` npm package against the isolated runtime DB copy — not via an MCP server.

> **Security note:** `.mcp.json` / `.vscode/mcp.json` hold credentials (e.g. a GitHub PAT) for the servers above. Both are git-ignored — **never commit them**, and treat any token that ever ends up in git history as compromised and rotate it immediately. Use `.env` in `banking-app/backend/` the same way for API secrets.

## 🏷️ Test Tagging & npm Scripts

Scenarios are tagged in the `.feature` files (`@Smoke`, `@Regression`, `@UI`, `@API`, `@DB`, `@Integration`, `@Accessibility`, `@Security`, `@BusinessRule`, `@KnownGap`, `@PerformanceSmoke`, ...), and `npm` scripts run subsets via `--grep`:

| Script | Runs |
|---|---|
| `npm test` | Everything |
| `npm run test:smoke` | `@Smoke` |
| `npm run test:regression` | `@Regression`, excluding `@KnownGap` |
| `npm run test:known-gaps` | `@KnownGap` — documented application gaps, expected to stay red until fixed |
| `npm run test:security` | `@Security` |
| `npm run test:accessibility` | `@Accessibility` (axe-core scans via `AccessibilityScanner`) |
| `npm run test:performance` | `@PerformanceSmoke` |
| `npm run test:ui` | `@UI` |
| `npm run test:api` | `@API` |
| `npm run test:db` | `@DB` |
| `npm run test:report` | Opens the last Playwright HTML report (`reports/html`) |
| `npm run allure:report` | Regenerates and opens the Allure report from `reports/allure-results` |
| `npm run bdd:gen` | Runs `bddgen` explicitly to (re)generate `tests/.features-gen` — required at least once before `npx playwright test` will find any tests (see [CI/CD](#-cicd)) |
| `npm run typecheck` | `tsc --noEmit` |

Every `test:*` script runs through `scripts/run-with-allure.js`, which always regenerates the Allure report afterward — pass or fail — so a failing run still produces a report instead of silently skipping it.

## ▶️ Running the App Under Test

You normally **don't** need to start the app manually — `config/global-setup.ts` spawns an isolated backend + frontend pair (against a fresh runtime copy of the seed DB) automatically before any test run, and `config/global-teardown.ts` tears them down afterward.

To run the app standalone (e.g. for manual exploration or when driving it via the `playwright-test` MCP server directly):

```bash
# Terminal 1 — backend (http://localhost:3000)
cd banking-app/backend
npm start

# Terminal 2 — frontend (http://localhost:3001, proxies /api → :3000)
cd banking-app/frontend
npm run dev
```

Verify the backend is healthy:
```bash
curl http://localhost:3000/api/health
# {"status":"Banking API is running"}
```

## 🧪 Running Tests

From the repo root:

```bash
npm test                          # full suite, all projects (chromium/firefox/webkit), with Allure report
npm run test:ui                   # just @UI-tagged scenarios
npm run test:api                  # just @API-tagged scenarios
npm run test:db                   # just @DB-tagged scenarios

npx playwright test               # same, without the Allure wrapper
npx playwright test --project=chromium
npx playwright test --ui          # interactive UI mode
npx playwright test --grep @Smoke --grep-invert @KnownGap
```

**Coverage** — 10 feature files under `features/`, driving:
- **UI layer** — full page-object-model flows: login, customer search/directory, customer profile CRUD, account management, fund transfers, session/token handling, accessibility (axe-core) and security (XSS/injection) checks, and a full keyboard-only end-to-end banking journey.
- **API layer** — direct HTTP assertions against `http://localhost:3000/api/*` via `ApiClient`/the per-resource API services.
- **DB layer** — direct SQLite assertions via `DbService`/the `db` fixture against the isolated per-run copy of `banking.db`, cross-checked against UI/API state (e.g. confirming a transfer actually moved balances between two `accounts` rows).

`chromium` runs the full suite (including `@API`/`@DB`-only scenarios); `firefox` and `webkit` re-run only `@UI`-tagged scenarios, since cross-browser rendering is what they exist to catch.

## 💾 Database Schema

`banking-app/backend/db/banking.db` (SQLite — single persistent connection, WAL mode)

**customers** — `id`, `firstName`, `lastName`, `email`, `phone`, `dateOfBirth`, `address_street/city/state/zipCode/country`, `createdAt`, `updatedAt`

**accounts** — `id`, `customerId` (FK), `accountNumber` (unique), `accountType`, `balance`, `currency`, `status` (`ACTIVE`/`INACTIVE`), `createdAt`, `updatedAt`

**transactions** — `id`, `accountId` (FK), `type` (`DEBIT`/`CREDIT`/`TRANSFER`), `amount`, `description`, `reference`, `status` (`PENDING`/`COMPLETED`), `createdAt`, `updatedAt`

**users** — `id`, `username` (unique), `email`, `password` (bcrypt hash), `createdAt` — auto-created on first `/auth/register` call

> Known gap (tagged `@KnownGap` in `customer_profile_management.feature`): deleting a customer does not cascade-delete their accounts/transactions.

## 🔄 CI/CD

`.github/workflows/playwright.yml` runs on push/PR to `main`/`master`, and can also be triggered manually (`workflow_dispatch`):

1. `npm ci` (root framework deps)
2. `npm ci` in `banking-app/backend` — **required**: it's a standalone `package.json`, not an npm workspace, so the root install alone never pulls in Express/sqlite3/etc.
3. `npm ci` in `banking-app/frontend` — same reasoning, for the Vite/React deps
4. `npx playwright install --with-deps`
5. `npm run bdd:gen` — **required**: `defineBddConfig()` computes the generated test directory but does not regenerate it as a side effect of loading the config on a clean checkout; only the explicit `bddgen` CLI does. Skipping this step passes CI right up until the "Run Playwright tests" step, which then fails immediately with `Error: No tests found`.
6. `npx playwright test`
7. Uploads the Playwright HTML report as a build artifact (30-day retention)

## 🐛 Troubleshooting

**Port 3000/3001 already in use**
```powershell
netstat -ano | findstr :3000
taskkill /PID <PID> /F
```

**`npx playwright test` can't find browsers**
```bash
npx playwright install --with-deps
```

**`Error: No tests found`**
Run `npm run bdd:gen` first — see the CI/CD note above. This directory (`tests/.features-gen`) is git-ignored and only exists after `bddgen` has run at least once.

**Backend can't reach the DB / `no such table`**
Check `DB_PATH` in `banking-app/backend/.env` and that `banking-app/backend/db/banking.db` exists — tables are created lazily on first request except `users`, which needs at least one `/auth/register` call. `db.js` uses a single persistent connection with WAL mode; if you see unexplained multi-second query latency under parallel test workers, that's the regression this fix addresses.

**Frontend shows blank screen after login**
Clear `localStorage` (`token`/`userId`) in devtools and log in again; check the browser console and confirm the Vite proxy in `banking-app/frontend/vite.config.js` points at the running backend port.
